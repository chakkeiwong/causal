54.1     An interface must preserve a scientific question
A servicing analyst asks whether an offer would improve the next twelve months’ net value
for accounts eligible today. A notebook, a scheduled command and an agent can all transmit
this question. They should receive the same conditional answer when they submit the same
declaration, inputs and method. They should also retain the same unresolved assumptions. A
successful call which replaces the target population, changes the sign or drops an unbounded
component of an uncertainty set has failed as a scientific interface even if its JSON is valid.
The preceding chapter establishes the exchange contract; this chapter develops the actual
access paths and the client behavior needed to preserve it.
   The implemented library entry is causalbank.runtime_v12.Runtime.invoke. The
command-line adapter and local MCP server use that runtime, its artifact store and the
scientific dispatcher. This shared implementation reduces divergence among surfaces. It does
not prove their equivalence: parsing, version negotiation, error handling and asynchronous
state can still alter the result seen by a client. Consequently an interface comparison must
examine complete canonical responses, including negative findings, rather than compare only
the estimated coefficient. The inspected source and recorded local trials support this narrow
architecture claim (Causal banking research project, 2026bf,n).
   The runtime advertises nine operations. Capability inspection reports the implemented
subset. Graph review checks a supplied declaration’s syntax. Identification attempts a supplied-
DAG back-door expression for independent units and a binary contrast. Estimation inverts
a Gaussian residual test using supplied moments and covariance. Sensitivity solves supplied
quadratic inequalities. Observation auditing checks declared timestamps. Report building,
job status and job cancellation provide the remaining three operations. Automatic problem
formulation, data-driven graph discovery and design comparison have no engine in this runtime.
They belong to the proposed architecture, and are absent from the advertised MCP tool list.
   These distinctions matter when an agent chooses a tool called estimate.effect. The
name identifies an operation family; the supported engine and estimator identifiers determine
what can actually run. An agent cannot turn the supplied-moment engine into a fitted causal
forest by changing its description. Nor does the graph syntax operation establish that a graph
represents the bank’s assignment mechanism. Capabilities should be inspected at the start
of a client session and retained with its results, because a proposed method and an installed
method are different inputs to a decision.

54.3     Calling the library and the command line
For the inspected installation, run Python with PYTHONPATH=src from the causal repository
root. The local environment is .runtime/in04/bin/python. The library use is small enough
to expose the whole boundary:
import json
from pathlib import Path
from causalbank.runtime_v12 import Runtime

request = json.loads(Path("request.json").read_text())

response = runtime.invoke(request)

The runtime root is an operator configuration inside this repository’s .runtime tree. The
scientific request has no field for choosing an arbitrary directory, Python module or shell
command. The library can still raise validation exceptions for malformed requests before
producing a canonical response; the caller must retain those as invocation failures. The
example assumes its displayed valid request (Causal banking research project, 2026n).

54.4     Conditional identification and a useful refusal
For the declared graph, adjustment for X blocks the back-door path A ← X → Y . Let
Y (a) be the potential net value under offer state a. Consistency, conditional exchangeability
Y (a) ⊥ A | X, positivity on the target population’s support, and the declared sampling
interpretation give
                          Z
            E{Y (a)} =        E{Y (a) | X = x} dPX (x)
                          Z
                      =       E{Y | A = a, X = x} dPX (x),
                          Z
                    τ=        [E{Y | A = 1, X = x} − E{Y | A = 0, X = x}] dPX (x).

The first equality averages over the target risk distribution. The second uses the identifying
assumptions. The resulting units are USD per account over the declared horizon. This
derivation explains the returned adjustment_contrast: integrate over risk, take the one-
versus-zero contrast, and retain the outcome unit and independent-unit sampling declaration.
It is an application of the identification argument developed earlier in the monograph; the
execution confirms the expression and its metadata, not the causal premises (Causal banking
research project, 2026n).
   Two counterexamples clarify the consumer’s next action. If the sampling field is changed
to dependent months, the local identification routine returns unsupported. It is refusing
a request outside this implementation’s scope; it has not proved that a panel estimand is
unidentified. The appropriate next step is a reviewed longitudinal or dependent-sampling path.
Changing the field back solely to make the call succeed would conceal a scientific problem. If
a declared premise is marked contradicted, identification instead returns refused, with no
scientific result. The premise or target must then be reconsidered; an automatic retry with
unchanged information has no scientific benefit.
  Even within a supplied DAG, failure of the selected back-door attempt is not a general
nonidentification theorem. An alternative graph assumption or identification strategy may
succeed, while another query may require only a bound. The service states the failed method’s

54.5      Uncertainty sets are part of the result type
A response may carry a set without a scalar estimate. To understand why the client must
preserve its topology, consider the explicitly generated inequality ab2 + cb + d ≤ 0, where b is
a scalar effect coordinate. Coefficient units are understood to make the terms commensurate;
the example uses a fixed normalized USD coordinate. The deterministic sensitivity operation
returns the solution set. Four elementary choices give independent algebraic checks of the
numerical representation:

Inequality             Real solution                  Canonical interval array
b2 − 4 ≤ 0             [−2, 2]                        [[-2,2]]
b2 + 1 ≤ 0             ∅                              []
−b2 − 1 ≤ 0            R                              [[null,null]]
−b2 + 4 ≤ 0            (−∞, −2] ∪ [2, ∞)              [[null,-2],[2,null]]

The first and fourth follow by comparing b2 with four. The second is empty because b2 + 1
is strictly positive; the third is the whole line because −b2 − 1 is strictly negative. In these
interval arrays null denotes an unbounded endpoint according to position, not missing data.
An unknown set has a different representation: unknown topology and null intervals. All four
arrays agreed between the library and CLI and with these independent calculations. Their
uncertainty kind is sensitivity, coverage is none, and the probability level is null (Causal
banking research project, 2026n).
   An empty result is not a numerical failure and is not evidence of a zero effect. It can mean
that the stipulated restrictions have no joint solution. A whole-line result supplies no finite
restriction on this coordinate. For the disconnected result, taking the convex hull discards
the excluded central region; truncating the tails fabricates information. A client chart should
retain the two rays and label their interpretation. A lending decision that requires a guaranteed
positive net benefit cannot infer it from a set containing an unbounded negative ray.

54.6      Four different meanings of success
Transport success, invocation completion, scientific disposition and qualification answer different
questions. The first says a reply arrived. The second says the operation finished. The third
distinguishes a computed object from an unsupported, refused or unavailable scientific result.
The fourth records what evidence supports using that object. A proposed client must preserve
all four, because none is a substitute for the next.
   The observed examples illustrate the distinction without a hypothetical failure rate. The
back-door request completed with a computed expression and conditional-inference qualification.
The unimplemented discovery request and the dependent-sampling request completed with
an unsupported disposition. The contradicted-premise request completed with a refused
disposition. All four returned CLI exit zero. In contrast, changing the sign convention
while reusing an artifact bound to the old context produced a failed canonical response,
invalid_or_unavailable_input, and exit four. Adding an undeclared request property
produced an adapter validation error and exit two (Causal banking research project, 2026n).

This is an adapter rule, not a universal classification of root causes. The runtime catches some
artifact access failures itself, returning a failed envelope that leads to exit four. Thus “artifact
problem” does not imply exit three. A client should branch on the actual response and record
the underlying cause, instead of guessing it from a coarse return code.
   For decision use, a conservative proposed display sequence is: validate and retain the
response; check operation and context identity; inspect execution status; interpret scientific
disposition; then render the typed result with its assumptions, uncertainty and qualification. A
computed timestamp diagnostic can contain failed rows. A computed set can be the whole line.
A completed identification operation can leave estimation entirely undone. The user-facing
conclusion should express these facts directly, rather than use a green success icon as a surrogate
for a supported financial decision.
   The same distinctions constrain automated repair. Malformed dates may admit a docu-
mented format correction. Missing causal assumptions require new information or an explicitly
changed problem. An unsupported engine may require another implementation. A weak-
information set may be the correct answer. A loop that retries until it obtains a positive scalar
would replace scientific reasoning with selection on favorable outputs.

54.7      Context binding, artifacts and observation time
Large or reusable inputs enter through the local artifact store. An operator can import a
JSON document with the CLI’s artifact put command, declaring its schema version and
role. For example, a prepared moments.json can be imported as follows:
PYTHONPATH=src .runtime/in04/bin/python -m causalbank.cli_v12 \
  artifact put --schema-version moment-summary/1 \
  --role moment_summary < moments.json

The returned descriptor goes into artifact_inputs; the complete descriptor, not merely a
guessed path, is the authorization declaration checked by the local runtime. The file must
contain the supplied means, covariance, sample-size and uncertainty settings required by that
operation, including its context digest. Other input roles have different schemas. This import
operation checks bounded JSON and identity; it does not certify that moments were correctly
estimated or that an operator chose a truthful schema label (Causal banking research project,
2026n).
  Let J(C) be the deterministic finite JSON serialization used by the implementation and
hC = SHA256(J(C)). An input moment, quadratic or observation artifact carries hC ; the
operation compares it with the digest of the submitted context. The digest binds target,
population, variables, intervention, horizon, units, sign, clock, sampling, assumptions and
graph together. Object-key order is normalized; ordered arrays remain ordered. This is
byte-level declaration identity, not a proof of semantic equivalence between two differently
expressed targets.
  Suppose a numerical provider prepared moments for offer-minus-no-offer. A client then
changes the displayed question to no-offer-minus-offer and reuses those moments. The context
check refuses that mismatch. To perform a legitimate sign conversion, the provider must
actually transform the numerical object and issue a new bound declaration. Simply copying a
new digest into unchanged input bytes can satisfy a structural check while lying about the
computation; the local system does not claim to defeat a dishonest operator. Its guarantee is
that an unnoticed declared mismatch is detected, with provenance available for review.
  The artifact identifier also includes the content hash and descriptor, including schema, role,
byte count and custody label. Reads compare the submitted descriptor with saved metadata
and verify bytes and hash. Files must be bounded nonsymlink regular files. These rules detect
accidental mutation and prevent request-specified filesystem traversal within the implemented
boundary. They do not establish a multi-tenant authorization service. Every caller using the
same operator store is operating inside the same local custody model.
  The clock example shows why metadata retention has scientific consequences. The imple-
mented diagnostic requires timezone-aware timestamps satisfying

                                   tevent ≤ tavailable < tdecision .

An event that happened yesterday but became available after the offer decision cannot support
a claim that its measured value was a baseline covariate. The three generated rows contain a
valid earlier observation, availability exactly at the decision, and a missing availability field.
The latter two are flagged. Passing this check establishes timestamp consistency only; source
ownership, measurement truth and inclusion mechanisms remain unverified. The proposed
client should therefore retain both the row diagnostics and the causal declaration explaining
why a field is an admissible adjustment variable.

54.8      MCP negotiation and client interpretation
The real local MCP adapter uses Python SDK 1.27.0 and protocol 2025-11-25 over standard
input/output. Its launch command is
PYTHONPATH=src .runtime/in04/bin/python -m causalbank.mcp_server_v12

A compatible client launches the process, negotiates the protocol and sends protocol messages.
The command is not a natural-language console. The inspected specification reserves stdout
for newline-delimited JSON-RPC messages and allows diagnostic text on stderr. Mixing a
startup banner with stdout would corrupt the transport even if the causal dispatcher were
correct (Model Context Protocol contributors, 2026e).
   Initialization is the first exchange. The client sends its supported version and capabilities; the
server returns its version and capabilities; the client then sends notifications/initialized.
A server that cannot use the requested version can return another supported version. If the
client cannot use the returned version, the specification says it should disconnect. Normal
operations must respect the negotiated capabilities (Model Context Protocol contributors,
2026c). The local adapter restricts negotiation to its tested legacy revision. Receiving a
response to initialization is therefore insufficient: the client must inspect what version was
actually selected.
   After initialization, tools/list exposes only the nine implemented operations, with input
and output schemas. For this example, causal_identify_effect accepts the complete
canonical request as the arguments member of a tools/call request. The protocol request
identifier correlates that exchange; the canonical request identifier inside the arguments
correlates the scientific operation. They need not be equal. The tool name must map to the
operation inside the request. Changing only the outer name does not relabel an identification
request as a discovery request (Causal banking research project, 2026bf).
   The server returns the canonical response in structuredContent and as serialized JSON in
a text-content block, following the inspected tool specification’s compatibility recommendation.
A client that supports structured content should validate it against the output schema and
retain the scientific fields. A client using the text copy must parse that JSON, rather than ask
a model to invent a convenient summary of it. A discrepancy between representations is an
interface defect to investigate (Model Context Protocol contributors, 2026f; Causal banking
research project, 2026bf).
   There are three distinct negative-result layers. An unknown tool is a JSON-RPC protocol
error, with the recorded adapter returning code −32602. A tool execution or input-validation
failure is a tool result with isError=true. A scientifically unsupported or refused request can
be a successful tool execution whose canonical disposition explains that no requested effect was
computed. The inspected legacy tool specification distinguishes the first two layers; the third
is the causal service’s own typed scientific meaning. A client which interprets isError=false
as “causal conclusion accepted” discards that meaning (Model Context Protocol contributors,
2026f; Causal banking research project, 2026n).
   Resources have a similarly explicit boundary. The protocol supports resource listing and
reading; the local adapter exposes only reports, evidence summaries and canonical responses no
larger than 65,536 bytes. Raw input roles are excluded. Reads use opaque causal-artifact
identifiers and repeat identity, role and size checks. An external model can nevertheless
receive sensitive information if the calling client sends it a readable summary containing
that information. Excluding raw roles is not content redaction, consent management or a
proof that a report contains no customer data. Those policies belong in any proposed bank-
facing wrapper (Model Context Protocol contributors, 2026d; Causal banking research project,

54.9       Replay, report jobs and cancellation
A client can lose a response after the work has completed. Retrying without an identity may
duplicate work; reusing an identity for a changed question may return a scientifically irrelevant
result. The implemented synchronous replay cache binds the optional idempotency key to a
digest of the request, excluding its correlation identifier and the key itself, and to the source and
selected execution environment: Python and the recorded numerical/schema package versions.
It is not an identity of every installed package or the host operating system. Inputs, operation,
context, parameters and budget remain part of that identity (Causal banking research project,
2026n).
   The generated capability example changes only the request identifier and recovers the same re-
sponse with the new correlation identifier. It then changes the wall budget from twelve to eleven
seconds under the same key; the runtime rejects the request with idempotency_conflict.
This result is deliberate: a changed execution contract is not an exact retry. A revised analysis
should use a new identity and explicitly state which earlier result it supersedes. The cache can
also preserve a failed response, so a client should not expect repeated use of the same key to
perform fresh attempts until one succeeds.
   Report building has a durable lifecycle. An operator supplies one to one hundred distinct
canonical-response artifacts. The runtime validates their schemas and creates a job bound to
input hashes, request, source, environment and budget. Submission returns a queued handle
even if the worker has already finished by the time the client receives it. The client uses the
handle in a job.status request. The returned envelope can itself be completed because the
status query succeeded, while result.payload.state says that the report is queued, running,
failed, cancelled or completed. The latter field determines the report’s state; the outer status
determines the query’s state.
   The executed report example summarizes the computed back-door response, the unsupported
discovery response and the refused premise. It preserves those three declarations and labels
verification as schema_only_not_causal_or_external_review. Resubmission with the same
identity returns the original handle and a queued submission envelope. It does not create
a new scientific review or promote the unsupported input (Causal banking research project,
2026n). The proposed user interface should display the final report only after a completed
payload state exposes its result reference, and should inspect each input’s declared status
before presenting a combined conclusion.
   Recovery is bounded. Completed work identifiers form an ordered prefix of the frozen input
list; checkpoints bind that prefix and the accumulated summaries to the execution identity.
The local runtime uses atomic state publication and a worker lease, allows at most three spawn
attempts, and retains the original deadline. Restart cannot silently add time, switch code or
accept altered checkpoint content. These mechanisms support local report recovery. They do
not establish distributed consensus, platform failover or universal exactly-once side effects in

   Cancellation also has two scopes. The protocol’s optional cancellation notification concerns

state. In the generated example, cancellation after completion leaves the completed report
intact. For a bank-facing workflow that actually sends offers, cancellation and compensating
actions would require a further design: this report service does not send offers or reverse
financial transactions.


54.10      Resource limits and deployment alternatives
Resource limits belong in the client contract because a mathematically well-formed request
may be infeasible in its launch environment. The local runtime bounds requests to one million
bytes, stored artifacts to eight MiB, worker address space to between 64 MiB and four GiB,
and worker wall time to at most 300 seconds. Artifact reads also respect the request’s memory
declaration. The worker runs a fixed internal entry point, with single-thread numerical settings;
the request cannot select arbitrary executable code. A small control error may exceed an
unrealistically tiny output limit so that the refusal remains explainable (Causal banking
research project, 2026n).
   These are implementation bounds, not service-level guarantees. The worker’s address-space
limit does not cover the resident coordinator or MCP SDK. End-to-end elapsed time includes
validation, process startup, transport and client handling. A process can fail while importing
dependencies under a small memory allocation. The client should report the actual execution
failure instead of claiming that the causal problem has no answer. A future service needs
measured admission limits for the chosen workload and its whole process tree, together with a
storage-retention policy and failure handling for exhausted capacity.
   Library use is the natural first option for a Python research workflow: it avoids protocol
negotiation and keeps canonical objects accessible to local code. It also places runtime
dependencies and exception handling in the consumer’s environment. The CLI provides a
process boundary and a simple JSON exchange for schedulers and language wrappers, with
explicit parsing and exit handling. It incurs process startup and requires artifact custody to be
arranged between invocations. MCP provides discovery and typed tool access for a compatible
agent client, but introduces protocol-version, transport and model-exposure questions. These
are different operational tradeoffs over the same scientific dispatcher.
   An R, Java or C++ consumer can in principle launch the CLI and preserve the JSON contract
without importing Python into its process. That is a proposed integration route, not evidence
that every such client works. A foreign function interface could reduce serialization costs for
intensive numerical work but couples runtimes and memory management. An HTTP service
could centralize dependencies and custody but adds authentication, network failures, multi-user
resource management and remote artifact authorization. The prototype recommendation is to
begin with the simplest surface matching the consumer’s actual needs and verify a complete
workflow before adding another boundary. The following chapter examines named workspace
consumers and their scientific mappings.

independently derived set shapes, weak moments, changed-context rejection and strict obser-

terminal-state interpretation and non-rollback after completion. They add reader-usable
demonstrations; they are neither a rerun of MCP conformance nor a statistical performance
study (Causal banking research project, 2026n).
   For the next actual consumer, the useful acceptance example is a complete decision trace.
Start from its target and data dictionary, retain the population, unit, sign, horizon, clocks and
assumptions in the request, select an implemented method, and examine both a supported
and a decision-relevant negative case. Verify that the consumer preserves uncertainty topology
and qualification when storing, plotting and exporting the result. Include an interrupted
or lost-response scenario with a stable identity, and check that recovery neither repeats an
external action nor silently changes the scientific problem. External actions remain outside
this reference implementation and require their own contract if introduced.
  This evidence would justify a scoped prototype connection. A claim of bank deployment
would additionally need the bank’s data and access policies, the intended platform’s operating
evidence, independent scientific review and acceptance of the actual financial workflow. The
proposal can already specify the connection and its decisive tests without pretending that
those later observations have occurred. The design contribution here is concrete: one scientific
object survives three access paths, and every client has explicit obligations for recognizing
what that object does and does not say.


54.12      Admission precedes interpretation in a causal client
The three surfaces become useful to a consumer only when the consumer can decide what
kind of reply it has received. Consider a scheduled lending report that asks for a conditional
adjustment expression, saves the reply, and later displays it through an agent. The numerical
estimate is correctly absent. If the final client converts that absence to zero, the report now
asserts a null monetary effect that no component calculated. If it displays only a successful
process status, the unsupported and refused cases look equally favorable. The missing product
component is therefore a reviewed client interpretation contract, with an explicit boundary
between receiving bytes, admitting a response, and deciding how that response may be used.
   A proposed client session should retain its launch configuration and admitted server identity,
the negotiated protocol where applicable, the operation catalogue and schemas, and the exact
scientific request. The catalogue is evidence about available operations in that session. It is
not a warranty that every graph class or estimator mentioned in a description is supported.

54.12.1     A narrow decoding profile with explicit failure states

First establish the transport boundary. A CLI consumer has process exit, stdout and stderr
as separate observations. A protocol consumer has a correlated protocol reply or a transport
failure before any causal response exists. Diagnostic output should be retained separately from
the object to be decoded. Stripping an arbitrary prefix until some braces can be parsed would
hide a corrupted channel and could select the wrong object from a mixed output stream. The
proposed local profile accepts one complete JSON value at the expected boundary, subject to
its byte allowance. It rejects a banner or trailing unrelated text. This is a deliberate consumer
restriction, not a claim that every possible transport framing uses one JSON document.
   The profile also rejects duplicate object keys, nonfinite numeric tokens and numeric overflow
that becomes nonfinite after parsing. Duplicate keys matter because two parsers can choose
different values for the same field. A reply containing both a completed and a failed status
under the same key has no single admitted meaning in this profile. Permitting a nonfinite
number as a point estimate would also bypass the explicit representation of unbounded sets.
The decoder consequently checks both the lexical input and the parsed numeric tree. A finite
byte limit reduces the amount of accepted input but does not by itself bound all parsing
memory or nesting depth; a deployment must add and measure those resource boundaries.
   After decoding, validate the full request and response schemas and the semantic relation
between them. The local semantic validator checks request and operation identity, the context
digest, units, result state, interval topology and uncertainty interpretation. For example, a
result marked uncomputed cannot carry a numerical estimate, and a sensitivity result has no
sampling-confidence level. These are testable declared relationships. They do not establish
that the graph or supplied covariance is true (Causal banking research project, 2026n). The
proposed client should keep schema admission and semantic admission as separate diagnostic
steps so that a missing field does not become a scientific claim of nonidentification.
   The finite reference applies the existing semantic validator to eleven preserved library/CLI
fixtures and classifies their meanings. It separately rejects duplicate keys, a nonfinite token,
overflow, trailing text, a banner, an excessive byte count, a wrong request identifier, a
wrong operation, a wrong context, inconsistent set topology and an unsupported response
carrying a numerical result. A twelfth adverse case compares conflicting structured and text
representations. The exercise uses local stored responses and deliberate copies; it makes no
network call and does not constitute a new MCP transport trial. Its scope is the proposed
semantic consumer, not complete schema, SDK, parser-resource or deployed-client qualification
(Causal banking research project, 2026az).

canonical response. A proposed client that consumes both should decode them separately and
compare their canonical finite JSON representations before interpreting either. Object ordering

54.12.4    Lost replies, stale observations and consumer state

The client needs its own durable record of an attempt. A timeout after submission does
not establish that the server did no work. If a stable idempotency identity was supplied,
the consumer can use the permitted replay or status path and retain the original request.
Changing the scientific context or budget while keeping the same identity requests a different
computation and should follow the conflict branch. The current implementation binds the
selected execution environment as well as the request, so replay after a source change can
be rejected even when the business sentence is unchanged. That rejection is evidence about
compatibility, not a failure to understand the user’s wording (Causal banking research project,
2026n).
   Polling introduces observation order. Suppose one status request begins before completion
but its response arrives after a later request that saw the completed state. A naive display
that overwrites its state with every arriving reply can regress from completed to running. The
proposed client should associate observations with the exact job and request identity and apply
a declared terminal-state rule. Under an immutable job identity, a terminal observation is
not replaced by a later-arriving nonterminal observation. Conflicting terminal states require
reconciliation with the authoritative job record; choosing the more favorable state is not a
repair. This is a proposed consumer rule and an adverse case for a future real transport
test, not a claim that the finite semantic reference simulates network ordering or distributed
consistency.
   Cancellation has the same distinction between a request and an observation. Recording
that the user requested cancellation is compatible with a final completed job when publication
won the race. The client should preserve both facts and label the resulting report accordingly.
It must not equate closing a window, cancelling a protocol call, requesting job cancellation
and undoing an external financial action. The actual service exposes report jobs and does not
perform those external actions. A consumer that later adds them needs a separate authoritative
reconciliation contract, not just another status string.


54.12.5    Capability negotiation determines a feasible workflow

A proposed workflow planner should admit a chain of operations only when each step’s typed
output can satisfy the next step’s input domain. A back-door expression is not a moment-
summary artifact; a graph suggestion is not a validated causal DAG; a successful timestamp
diagnostic is not an assignment mechanism. Therefore operation-name agreement alone cannot

   For each candidate route, the planner should compare the declared target, graph class,

invalidates every earlier scientific result.

admission trace, followed by an optional explanation layer. Its evaluation should pair each
supported result with an appropriate negative case and inspect the stored and exported
objects, not merely the screen caption. The finite reference already makes specific decoding
and interpretation errors reproducible. Completing an actual client would add full schema
validation, bounded parser resources, live transport ordering, artifact retrieval, custody policy
and launch-environment trials. These are known engineering steps justified by the proposal.
They remain separate from expensive bank experiments, which should follow only after the
prototype demonstrates useful preservation of the scientific question.
