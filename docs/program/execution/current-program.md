## Execution loop

1. Read `status`, `check` and `next`. If an operation is active, resume its exact checkpoint. Otherwise start the next eligible operation with `start`. Work-selection overrides need a reason. No phase, document publication or review checkpoint creates a permission gate.
2. Perform the selected work. Before final studies, freeze and register the real protocol, including code/data identities, alternatives, failed requests and fixed stopping rules. A design task is not an executed study.
3. Review the result against every task criterion. Use `template ID` for the receipt schema; every finding needs hash-bound evidence. Use `record ID --receipt PATH` only for actual reviewed outcomes. Negative and inconclusive findings are retained without inventing execution or qualification.
4. For partial work, `progress ID --receipt PATH` saves observed findings, evidence and an exact next action, keeping it active across interruption. Use `yield` only with a recorded reason and checkpoint when switching to another independent task. A checkpoint is not a reason to end execution.
5. If a real prerequisite is unavailable, `block ID --receipt PATH` records evidence and an exact revisit trigger, then selects independent work. `resume` requires evidence that the blocking condition changed. A locally blocked source, theorem or platform cannot stop other ready branches.
6. After every outcome or local blocker, read the returned next action and continue. End master-program execution only when its accepted scope is complete, the user asks to stop, no authorized work is eligible, or a real session/tool constraint prevents further work. In the last case preserve the active checkpoint and describe the constraint honestly. A final reply does not launch a background agent.

The scheduler rotates among public-evidence, software, reuse, commercial, LLM, integration, research, manuscript, external-preparation and release work. An interrupted active task takes precedence. The six public designs share the same lifecycle and selection as the preserved 416 operations. None awards bank product or adoption acceptance.

When a recorded Q1–Q5 review concerns an earlier reader, or a negative review has been repaired, use `reopen ID --receipt PATH`. This is an evidence transition, not a permission request. The note binds `prior_result`, the exact current `reviewed_reader`, a `reason`, `evidence` and an exact `next_action`. The controller preserves the previous receipt and its prerequisite identities in review history and resumes the review. It does not reopen ordinary completed work or a passing review of the same reader. After reopening, `template ID` supplies a new immutable output path containing the reader hash and review attempt; never overwrite an earlier review file.
