## Repair reviewed before execution

The chosen repair adds one stable current entrypoint and a small contract supplement. It joins P1–P6 and receipt-based Q1–Q5 reviews to the existing graph in memory. It keeps the original bound graph, scope, controllers, papers, study results, PDFs and receipts unchanged. A single canonical state stores the new tasks and active checkpoint; historical operation receipts still use their original contracts and validators.

Rejected approaches were replacing the master program again without performing work; weakening qualification rules to obtain a green dashboard; placing bank inputs on proposal paths; and presenting a scheduler as an autonomous research runner. A shell loop over these tasks cannot perform scholarly judgement and would create empty or fabricated outcomes.

The review requires tests of public-task completion and advancement, interruption recovery, local-blocker isolation, tampered/missing evidence, duplicate completion, stale state writes, proposal/later-stage separation, final-study registration and acceptance without actual reviews. Both new and historical controllers must still validate the resulting canonical state. Test results and exact code identities are recorded in `verification.json` before installation.

Execution must demonstrate the repair by producing reviewed public task designs and substantive existing-graph work, recording their actual outcome rather than stopping after this document. Design checks are explicitly development work, not held-out model evaluation or new causal studies. The live dashboard supplies remaining counts and next actions; this review preserves the pre-repair diagnosis.
