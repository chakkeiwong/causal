# Recover the scientific request as well as the computation

The proposed causal library should reuse suitable scheduling and storage services while owning an explicit scientific request contract. A successful job, a reused output and an unchanged task graph each answer an operational question. None alone establishes that every requested causal target was evaluated for the intended population and information clock. The comparison therefore concerns how existing recovery mechanisms interact with the target, failure denominator, provenance and total cost. The current monograph develops these mechanisms and exact counterexamples in its computation chapter. This focused comparison completes the separate scientific synthesis; it does not close the commercial landscape survey. \citep{exec22_workflow_reference,exec23_dss_denominator_reference}

## Existing mechanisms and the additional application contract

| Inspected mechanism | Documented behavior | Proposed causal-workload obligation |
|---|---|---|
| Databricks repair | Reruns failed tasks and dependents with current settings; unsuccessful tasks restart from the beginning. Partial append writes can duplicate rows. | Bind code/settings to the request, distinguish retry from changed analysis, and use unique/conflict-checked result commits while retaining every attempt. |
| Databricks monitoring | Leaf-task semantics can produce “Succeeded with failures”; current text documents 48-hour graph and 60-day history displays. | Keep a durable requested-unit ledger and actual run identity rather than inferring denominator completeness from job success or a display. |
| Snowflake task graphs | Execution dependencies, overlap and retry controls; suspended children can count as succeeded and a skipped root does not invoke its finalizer. Graph versions do not include called stored-procedure definitions. | Pin procedural dependencies, retain skipped requests, test conflicting writes and distinguish a scheduling DAG from a causal graph. |
| Azure ML API-v2 reuse | Requires declared determinism, ForceReRun=false and matching code, environment, inputs and settings; reused outputs display previous run artifacts. | Include immutable data, target weights, outcome clock and uncertainty settings among declared dependencies. A stable URI or determinism declaration does not prove scientific equivalence. |
| AWS Step Functions | Ordered retriers/catchers, backoff, jitter and retry limits; eligible retry counters reset on redrive. States.ALL omits DataLimitExceeded and Runtime, while the inspected current text permits explicitly named DataLimitExceeded handling. | Keep a lifetime attempt/cost ledger across executions; distinguish transient execution failure, unsupported scientific request and terminal runtime error. |
| Dataiku DSS scenarios | Sequential step controls, some error-to-warning conversions, conditional execution, suppression/squashing of triggers, selected SQL-query change rules, pytest and reference-flow comparisons. | Preserve all requested cohorts and fixed weights, define which events require distinct analysis, and test actual scientific dependencies rather than only row count or maximum date. |

These are supported observations from the saved official originals. The scientific column is a proposed application contract, not a finding that the vendor cannot implement it. Rights, actual prices, deployment behavior and native adapter qualification remain unmeasured. \citep{exec22_workflow_databricks_repair,exec22_workflow_databricks_monitor,exec22_workflow_snowflake_graphs,exec22_workflow_azure_reuse,exec22_workflow_aws_errors,exec23_dss_latest_flow,exec23_dss_latest_triggers,exec23_dss_latest_steps,exec23_dss_dss14_flow}

## Duplicate writes and missing effects change different denominators

For a finite declared population U, let tau_i be its stipulated dollar effect and define tau_U = sum(tau_i)/|U|. Three units have effect +6 and one -2, so tau_U=4. If two positive units are appended before a crash and all four appended after repair, the stored average becomes 14/3. The implicit positive-group weight has changed from 3/4 to 5/6. At a stipulated one-dollar cost, the net value changes from 3 to 11/3. Keyed recovery can restore four unique results when the scientific identity and commit semantics are correct, but the six attempts and their costs must remain recorded. Overwriting a key with a different target or data vintage is a conflict, not valid replay. These exact calculations have no sampling noise and are not observed vendor failures. \citep{exec22_workflow_reference}

Failure can instead remove an effect from the result. For two equal-weight cohorts with effects +10 and -30 and one-dollar contact cost, the all-contact versus no-contact policy has net value -11 per eligible member. Omitting the negative cohort and renormalizing to the returned cohort gives +9, a 20-dollar error and sign reversal. A failed, skipped or tolerated-without-effect request must still retain its requested weight. Reporting +9 for the returned cohort is legitimate only with that changed population stated. If a separate argument supplies the missing effect range [-50,50], the original target has net range [-21,29]. It is an assumed identification range, not a statistical confidence interval, and gives no guaranteed positive return. Recovering the missing effect, justifying tighter bounds or declaring a different policy are distinct remedies. \citep{exec23_dss_denominator_reference}

The same output can also become stale without any operational failure. Keeping effects (6,-2) while reversing weights from (3/4,1/4) to (1/4,3/4) changes net value from +3 to -1. Keeping the original weights but changing the last unit's effect to -10 yields gross effect 2. A separate two-cohort table can keep row count and maximum date fixed while the second effect changes from -30 to +30, changing net value from -11 to +19. Thus a cache key or trigger must cover the actual dependencies of the scientific question. A stronger SQL query remains possible; the counterexample concerns the selected count/date proxy. \citep{exec22_workflow_reference,exec23_dss_denominator_reference}

## Request identity, uncertainty and failure reporting

Define a proposed canonical manifest m(q) containing input snapshots, target population and weights, estimand, information clock, graph/identification assumptions, estimator and covariance settings, code/environment, seeds or coupled random streams, numerical tolerances and output schema. A digest binds the declared bytes, not the truth of the declarations or completeness of this dependency list. The library, CLI and MCP should transport the same manifest. Unique result commits refer to its identity; attempt records distinguish complete, refused, failed, skipped and reused outcomes. The requested count and each disposition count remain visible alongside accuracy, coverage and width among admissible outputs. A scientific refusal cannot become a successful number through a retry. \citep{exec22_workflow_reference}

Dataiku's default trigger suppression can leave a trigger unevaluated during a run; the manual also documents delay and squash behavior and exclusions for time/manual/hidden child-scenario triggers. A latest-snapshot analysis may intentionally combine changes, while a declared event study needs its eligible event set preserved. The initiating identity and actual child-scenario outcome must survive composition. The application must first define the event-to-request relationship and then qualify a compatible configuration. It cannot assume every raw data change is a scientific event or that trigger counts prove event completeness. \citep{exec23_dss_latest_triggers,exec23_dss_latest_steps}

Scientific uncertainty also survives recovery. Confidence-set components, infinite endpoints, unsupported targets and exhausted numerical searches must not collapse into a single missing-value field. Reusing a draw with changed weights, resuming with a new randomness coupling, or silently dropping failed fits can change the evaluated estimator. The reference examples establish exact accounting consequences; statistical calibration of any chosen runtime remains a separate registered study.

## Edition limits and the economical next experiment

The six earlier workflow manuals were acquired on 22 October. Databricks pages show post-cutoff updates; Azure's displayed March date and later repository metadata do not authenticate its historical technical bytes. Other mutable pages also lack exact cutoff revisions. The Dataiku release index places 15.0.0 and 15.0.2 before 7 October, and 15.1/15.2 after it. Current DSS 15 technical pages and matching DSS 14 step-control text still do not prove exact historical patch content. SAS Viya, Domino, Posit and complementary market discovery remain source work. These limits prevent current observations from silently becoming an exhaustive cutoff claim. \citep{exec22_workflow_databricks_repair,exec22_workflow_databricks_monitor,exec22_workflow_azure_reuse,exec22_workflow_snowflake_graphs,exec22_workflow_aws_errors,exec23_dss_latest_releases,exec23_dss_dss14_releases}

The initial investment should test a small frozen manifest with public schema data and separately generated known-truth effects. Include partial append, changed target weights, changed data under a stable identifier, changed procedure/settings, missing cohorts, skipped roots, conflicting commits, redrive and exhausted budgets. Verify results and all attempts against the independent exact references before comparing runtime. Whole-workflow cost includes transitions, compute, storage, transfer, review and license costs, including failed/recovery attempts without double counting. Actual rates and staff time need evidence. The proposal recommends an experiment capable of finding semantic failure before an expensive bank trial; it claims no measured savings, native vendor execution or bank return.
