\section{Discovery beyond the principal language interfaces}
\label{exec13:other-discovery}

A causal library can gain useful capabilities from Julia, Rust, MATLAB and
JavaScript without treating the programming language as evidence for a
scientific claim. Julia offers composable graph and independence-test
interfaces. Rust can supply numerical search behind an existing R or Python
interface. MATLAB contains influential reference implementations and older
toolboxes whose mathematical ideas remain useful even when their deployment
or licensing conditions are unsuitable. JavaScript can connect graph
construction to an analyst's conversation. These contributions belong at
different points in the proposed system.

The comparison develops eleven selected implementation families from source
revisions dated no later than 7 October 2026. It distinguishes algorithm
source, interface documentation and author performance claims. Broader
language and package-registry coverage remains incomplete: neither a missing
search result nor an uninspected repository establishes that an implementation
does not exist. The numerical examples below are exact project constructions,
not executions of the surveyed engines. Their purpose is to specify what a
future adapter must preserve before a speed or accuracy comparison would be
meaningful.

\subsection{The useful unit of comparison is the mathematical operation}

Table~\ref{tab:exec13-other-roles} gives the proposed disposition of each
selected family. Integration means retaining an engine behind a reviewed
input and result contract. Porting means taking responsibility for a new
implementation, including its numerical behavior, dependencies and applicable
terms. Adoption means making the dependency part of a supported product
path. A favorable source comparison can justify an integration experiment;
it does not complete any of these engineering obligations.

\subsection{A funding example distinguishes ambiguity from a matrix error}

Consider three jointly recorded quantities: a funding-pressure score $U$, a
quoted-rate change $Q$ in percentage points, and retained funding $F$ in
millions of US dollars. The score is a summary measured over the observation
window; its name alone does not establish that it precedes the quote. The
following centered linear Gaussian constructions stipulate three different
causal explanations. Disturbances are mutually independent within each
construction, with variances stated explicitly:
\begin{align}
\mathcal M_1:\quad &U=\epsilon_U,\quad
 Q=\tfrac12U+\epsilon_Q,\quad F=2Q+\epsilon_F,\\
\mathcal M_2:\quad &Q=\eta_Q,\quad
 U=\tfrac12Q+\eta_U,\quad F=2Q+\eta_F,\\
\mathcal M_3:\quad &F=\xi_F,\quad
 Q=\tfrac25F+\xi_Q,\quad U=\tfrac12Q+\xi_U.
\end{align}
In variable order $(U,Q,F)$, the disturbance variances are respectively
$(1,3/4,1)$, $(3/4,1,1)$ and $(3/4,1/5,5)$.
Each construction induces
the same covariance in variable order $(U,Q,F)$:
\[
 \Sigma=\begin{pmatrix}
 1&1/2&1\\1/2&1&2\\1&2&5
 \end{pmatrix}.
\]
For example, under $\mathcal M_1$, $\operatorname{var}(Q)=1/4+3/4=1$,
$\operatorname{cov}(U,F)=2(1/2)=1$, and
$\operatorname{var}(F)=4+1=5$. Under $\mathcal M_3$,
$\operatorname{var}(Q)=4(5)/25+1/5=1$ and
$\operatorname{cov}(Q,F)=2$. The other entries follow directly.
Because the laws are centered Gaussian, equal covariance here implies equal
observational distributions. Also
\[
 \operatorname{cov}(U,F\mid Q)
 =1-\frac{(1/2)(2)}{1}=0.
\]
The three graphs have the same undirected chain and no unshielded collider.
They differ in what a quote intervention does.

Replacing the equation for $Q$ with a value increased by $1/4$ changes
expected $F$ by $1/2$ in $\mathcal M_1$ and $\mathcal M_2$, and by zero in
$\mathcal M_3$. Thus the intervention response belongs to
$\{0,1/2\}$ million dollars in this declared three-model family. This is a
finite ambiguity set, not a confidence interval and not a claim about every
possible causal model for the observations. A justified observation clock
could exclude some of these explanations; the statistical column label
cannot do so by itself. Exact rational covariance and intervention
calculations reproduce the construction~\citep{exec13_other_exact}.

Now write a supplied structural model as $x=Bx+e$, so that $B_{ij}$ is the
coefficient from variable $j$ to variable $i$. For $\mathcal M_1$,
\[
 B=\begin{pmatrix}0&0&0\\1/2&0&0\\0&2&0\end{pmatrix}.
\]
The total $Q\to F$ slope is two. If an adapter transposes this matrix while
keeping the variable order and column-vector convention, the displayed graph
is still acyclic but its $Q\to F$ slope is zero. This is a conversion error
in a supplied model. It differs from the legitimate ambiguity across the
three observationally equivalent models: one should repair the conversion
error and preserve the genuine ambiguity.

Unresolved edges introduce another representation problem. A Julia
\texttt{DiGraph} may store both $i\to j$ and $j\to i$ to represent one
undirected edge. It is then a container for a partially directed graph, not a
claim that the causal system has a two-way feedback loop. A generic acyclicity
check applied before decoding will incorrectly reject that representation.
A generic linear-system solver applied to its zero-one adjacency will invent
coefficients and feedback. Both failures can occur without changing a single
stored byte.

\subsection{Julia: composability requires checking the actual dispatch}

CausalInference.jl 0.19.4 provides a useful starting point for a Julia
backend. Its inspected PC entrypoint accepts a conditional-independence
callback and defaults to the stable skeleton path. It returns a CPDAG in the
reciprocal-arc representation. Gaussian GES exposes a different computation:
forward insertion and backward deletion continue while a score improvement
is available. The selected function returns a graph, score improvement
relative to the empty graph, and timing information. Its default penalty is
$0.5$, which should not be confused with the explicit values used in examples
or with another library's score normalization
\citep{exec13_other_causalinference}.

The covariance-based local score makes this distinction precise. With $n$
rows, $k$ parents, penalty multiplier $\lambda$, and residual variance $C_p$,
the inspected expression is
\[
 s=-\tfrac12\{n[1+\log(\max(0,C_p))]
                +\lambda(1+k)\log n\}.
\]
For a nonsingular parent covariance block, $C_p$ is computed by subtracting
the explained covariance contribution. A larger value is preferred by the
search. If $C_p=0$, however, the displayed logarithm is not a finite number;
the zero clamp is not a positive numerical floor. The adapter should diagnose
constant variables, deterministic relationships, singular parent systems and
nonfinite scores before using a chosen graph in a funding decision. A
perfect numerical fit can signal degeneracy, not overwhelming causal
evidence. Score comparison across engines also requires matching centering,
penalties, constants and the exact returned quantity.

Associations.jl offers a broader composition of association measures,
independence tests and graph algorithms. That flexibility is useful when the
banking variables are nonlinear, but it does not make arbitrary compositions
valid. The PC documentation requires nondirectional pairwise and conditional
measures and specifically warns against inserting transfer entropy into this
generic symmetric skeleton procedure. The selected \texttt{check\_input}
contains the direction check only as commented code. The proposed wrapper
must enforce the compatibility condition itself and record which measure and
test were admitted~\citep{exec13_other_associations}.

Defaults also need source-level attention. The PC constructor uses
\texttt{maxdepth}, while the docstring presents \texttt{max\_depth}.
The local-permutation constructor defaults to ten neighbors, although its
documented signature says five. It exposes the number of shuffles, random
generator and a temporal exclusion window. These are concrete parameters of
the proposed statistical experiment. A temporal window alone does not prove
that a resampling scheme gives valid uncertainty for repeated accounts,
common market shocks or a changing assignment process. The parameter,
sampling unit and relevant null law must be reviewed together.

The selected skeleton removes an edge when the returned $p$-value exceeds
$\alpha$. This is a procedural choice made by the algorithm. Failure to
reject independence is not proof that the variables are independent,
especially with small samples or high-dimensional conditioning sets.
Likewise a finite orientation-sweep limit can leave the graph less fully
oriented than an unrestricted run. A result should disclose the restriction
and retain the partially resolved object, rather than infer a unique graph
from the fact that an execution completed.

RecursiveCausalDiscovery.jl 0.2.0 gives a narrower alternative. Its README
lists RSL-D as implemented while marking MARVEL, L-MARVEL and ROL as future
work. Its boundary initialization tests every pair conditional on all other
variables. That initial conditioning problem can be statistically difficult
even when a later recursive search reduces the number of tests. The selected
implementation also falls back to a smallest-boundary variable when it finds
no removable variable. The output alone does not reveal that the intended
removability condition was successfully established
\citep{exec13_other_recursive}.

A specific dispatch issue must be resolved before relying on separate
boundary and search tests. The matrix overload accepts a distinct
\texttt{mkbd\_ci\_test} argument but forwards \texttt{ci\_test} in its place
when converting to the table path. Source inspection therefore does not
support the claim that both overloads honor the supplied boundary test.
The README's Julia requirement and the broader manifest declaration also
differ. These findings justify retaining the package as an experimental
comparison, with explicit overload and environment checks. They do not
establish that recursive methods in general are unsuitable.

The three Julia families have inspected MIT grants. That makes a proposed
integration easier to pursue subject to the notices and dependency terms,
but creates no statistical warranty. The preferred first step is a restricted
Julia process with a frozen package environment, explicit table orientation
and graph decoder. Reimplementing every graph method in the common library
would add mathematical and maintenance obligations before demonstrating a
consumer need for the port.

\subsection{Rust: a native implementation still needs a statistical contract}

FLOP/flopsearch 0.3.0 already connects a Rust numerical search to Python and R.
Its selected interface accepts observations by rows, a BIC penalty and a
termination choice. It documents a CPDAG matrix with directed entries one and
unresolved entries two. This offers a plausible alternative to building a
new Rust foreign-function interface merely because the core is native
\citep{exec13_other_flopsearch}.

The stopping contract needs closer treatment than the word ``timeout''
suggests. The selected configuration requires exactly one of a restart
count, a timeout or manual termination. The Python stub states that at least
one local search runs to a local optimum. In the inspected Rust loop, the
shown abort check is conditional on being beyond the first restart; it exits
an inner search loop. The surrounding restart loop and delegated numerical
calls require further qualification before the product can promise a strict
elapsed deadline. A proposal adapter can impose an outer worker deadline,
but must then say whether interruption returns a validated best-so-far
graph, a checkpoint or only a failed request. It cannot imply that the
library's timer already provides the desired service guarantee.

The same entrypoint uses a thread-local random generator, while the selected
public configuration exposes no seed. This limits the replay contract that
can be promised from that interface alone. A frozen binary and dataset are
insufficient to establish identical stochastic output. Before a matched
benchmark, decide whether the adapter can bind the random state or must
compare declared output distributions over registered repeated runs. The
inspected MPL-2.0 grant also requires a distribution-specific review of
covered source and notices; using an existing wrapper does not remove that
obligation.

The static DirectLiNGAM path in varlingam-rs 0.1.0 presents a different issue.
Its coefficient assignment is explicitly $B[\mathrm{target},\mathrm{predictor}]$,
consistent with the column-vector convention used above. It selects an
ordering, uses a sparse predictor-selection step, and refits retained
predictors on their original scale. The README advertises matching accuracy
and substantial speedups, but those statements are not independent evidence
for the proposed banking workload~\citep{exec13_other_varlingam}.

The inspected ordering optimization constructs entropy summaries once.
Subsequent iterations update residual data, yet the root-scoring helper
ignores its data argument and uses the cached summaries. There may be a
mathematical argument for a particular cached formulation, but it has not
been established by reading the performance claim or this helper alone.
The appropriate next comparison freezes the intended algorithm, inspects
the optimization argument and delegated numerical helpers, and tests
matched cases where the evolving residual distribution matters. It would be
premature either to assert algorithmic equivalence or to declare every
cached strategy incorrect. The recommendation is to defer default adoption
and retain this as a candidate for focused review. Its inspected MIT or
Apache-2.0 choice resolves one part of reuse, not the algorithmic question.

why-rs 0.2.1 supplies a particularly clear reason to inspect code beneath an
algorithm name. Its selected PC propagation method implements one rule and
explicitly leaves the second and third rules for future addition. Its
independence calculation has hardcoded normal critical values for
$\alpha=0.01,0.05,0.10$; every other supplied value receives $1.960$.
The recursive partial-correlation calculation returns zero when its
denominator is zero. These are source-level findings about the pinned path,
not claims derived from executing a Rust benchmark~\citep{exec13_other_why}.

For example, a two-sided normal reference test at $\alpha=0.02$ would use
$\Phi^{-1}(0.99)\simeq2.32635$. At a stipulated statistic of $2.2$, that
reference does not reject independence, whereas the inspected fallback
$1.960$ does. Under an exactly standard normal reference law, the latter
threshold has rejection probability approximately $0.05$, not $0.02$.
This scalar calculation demonstrates a parameter mismatch; it does not
estimate an empirical false-positive rate for a whole discovery procedure
\citep{exec13_other_exact}. Returning zero for a degenerate partial
correlation can similarly turn an undefined calculation into an
independence decision. The proposed common adapter should preserve numerical
failure as a distinct outcome.

Together these findings justify rejecting this particular PC implementation
as the reference discovery engine. They do not require rejecting its graph
modeling or structural simulation ideas, which would need their own
inspection. A language with strong memory-safety features does not supply
missing orientation rules or validate a statistical reference law.

\subsection{MATLAB: reference value and reuse rights are separate}

Causal Explorer 1.5 documents a broad family of discovery and variable-selection
methods. Its PC manual specifies variables by columns, domain counts for
discrete variables, and mutual-information, $G^2$ or Fisher-$z$ choices.
The saved release states P-code compatibility with MATLAB R2017b. These
details make it a useful documented comparator, but neither they nor a
public repository establish an unrestricted source-code dependency
\citep{exec13_other_explorer}.

The accompanying license restricts the grant to noncommercial educational
and research use by an academic recipient on a single-user system, without
permission to redistribute or create derivative works. The manual's
``public domain'' wording cannot by itself resolve this conflict. Under the
saved grant, the proposed commercial library should reject direct adoption
and porting of this distribution. Separately obtained rights could change a
later decision. The proposal can already compare the documented capability
against alternatives whose reuse terms support the intended route. No
MATLAB execution, current platform compatibility or agreement to those
terms is implied by this comparison.

The generalized-score GES reference provides readable MATLAB search and
scoring code. Its selected criteria are negative cross-validated likelihood
or negative marginal likelihood, with separate paths for multidimensional
variables. The search seeks decreases in this criterion. This differs in
sign and meaning from the maximized Gaussian score described for Julia;
the raw numerical values are not a common ranking of engines. Its output
uses one for a directed edge and minus one for an unresolved edge, adding
another reason to decode by method identity
\citep{exec13_other_generalized}.

The inspected cross-validation score forms dense $T\times T$ kernel and
centering arrays for $T$ observations, computes data-dependent bandwidths,
and slices contiguous validation folds. One dense double-precision array
alone takes approximately $8T^2$ bytes before workspace, copies and other
arrays. This storage account follows from the array dimensions; it is not
a measured peak-memory benchmark. Contiguous slices do not automatically
constitute a valid forward-in-time banking evaluation. Training can include
observations later than the held-out block, and the displayed preprocessing
is computed before that block is sliced. A proposed dependent-data study
must explicitly decide what is known when, how kernels are constructed and
what the score is intended to validate.

The top-level GES rights also remain unresolved. The saved repository tree
contains a redistribution notice for an embedded kernel-test component,
but that grant does not establish permission for all surrounding code.
The immediate choice is to retain this methodological comparison and defer
redistribution or porting. A clean new implementation would still require
an inspected mathematical specification, independent verification and a
reason to maintain it alongside existing engines. Merely translating MATLAB
syntax would not resolve those obligations.

Bayes Net Toolbox provides a useful older reference for how distinct search
contracts coexist inside one toolbox. Its K2 entrypoint places variables in
rows and observations in columns. It greedily adds parents from predecessors
in a user-supplied ordering, with Bayesian or BIC score options. Thus the
ordering supplies directional restrictions that the procedure does not
learn. If a funding analyst orders quoted rate before retained funding,
the algorithm's inability to return a reverse parent is partly a consequence
of that input, not evidence against the reverse causal explanation
\citep{exec13_other_bnt}.

The selected BNT PC function instead accepts a conditional-independence
callback and returns a partially directed adjacency with negative one for
a directed edge and symmetric positive ones for an unresolved edge.
Data orientation, algorithm output and coefficient interpretation are three
separate conversions. Tests that verify only the number of rows or edges
will miss a semantic reversal. Its BNT license file explicitly uses the GNU
Library General Public License version 2; its name ending in
\texttt{license.gpl.txt} is insufficient to characterize every component of
the larger collection. Preserve the actual grant, review bundled components,
and test a selected modern environment before recommending adoption.
An old documentation date establishes neither current maintenance nor
current failure, and historical price references should not enter the
investment account as contemporary quotations.

\subsection{JavaScript: support the analyst without inventing an effect}

DAGitty's JavaScript core is a plausible component for constructing and
analyzing a proposed banking graph. Its selected adjustment interface
accepts DAG, PDAG, MAG and PAG types, reads source and target nodes, and
handles adjustment and selection information. The browser interface and R
frontend expose the same underlying family of graph operations
\citep{exec13_other_dagitty}. This is valuable for reviewing a claim such as
``adjust for the customer's prior relationship score.'' It does not prove
that the supplied arrows correspond to the bank's assignment process.

The intended integration therefore keeps graph authoring, graph analysis
and data-based discovery separate. An analyst can propose alternative
diagrams, attach an observation clock and identify whether an adjustment
query has an answer under each diagram. The proposed numerical service can
then report what estimation would require. The JavaScript graph must retain
its class and endpoint marks through those steps. Rendering a PAG as a DAG
to simplify an interface would give the analyst a stronger assumption than
the source result supports. The inspected GPL-v2 terms and dependency
notices require an appropriate distribution design; process separation
alone does not establish exemption from those terms.

The selected expert-in-loop JavaScript demo illustrates a more subtle
boundary. Its \texttt{pillai\_test} fits random forests for two variables on
the conditioning variables, predicts on those same rows, computes residuals,
and obtains canonical correlations. Its \texttt{effectSize} field is the
sum of squared canonical correlations, followed by an $F$-reference
calculation. The display logic can combine that statistic with an arrow from
the supplied graph~\citep{exec13_other_webapp}.

A squared canonical correlation is an association statistic. It is
dimensionless and does not provide the sign or monetary units of the
funding response above. Attaching an arrow to it does not turn it into
$\partial\mathbb E[F\mid\operatorname{do}(Q)]/\partial Q$.
Nor does the inspected formula establish a calibrated null distribution
after fitting flexible residual models on the same rows. A serious
integration would need a stated statistical target, an argument or measured
calibration for the actual fitting procedure, and appropriate held-out or
cross-fitted alternatives. The product can use the interface idea for
discussing disagreements while declining to display the statistic as a
banking treatment effect.

The package metadata declares ISC, while the selected tree does not supply
a complete top-level grant sufficient for this review. Its test command is
a placeholder that exits unsuccessfully. Neither fact proves that the
interaction idea is unusable; both prevent treating a successful package
installation or a license field as a completed adoption assessment.
The recommended next use is a separately designed graph-review interaction,
with any numerical comparison delegated to an admitted scientific method.

\subsection{An integration sequence that preserves useful alternatives}

The proposed first implementation should admit a small set of mathematical
operations. One Julia PC/GES path can test the independence and score-search
boundary; FLOP can test an existing native engine behind an R/Python
interface; DAGitty can test graph review and adjustment. Each has a concrete
reason to be considered. The unqualified Rust paths, unresolved MATLAB
rights and browser residual statistic need not block those independent
experiments. They remain explicit alternatives or rejected current choices,
with the condition that would change the decision.

A common adverse-fixture suite should verify both input and result meaning.
The funding construction supplies a weighted DAG whose transpose changes
the effect, an unresolved chain with several compatible effects, and graph
mark conventions that cannot be read as coefficients. Other fixtures should
include constant variables, singular covariance, a caller-supplied
nondefault significance level, changed variable order, a limited conditioning
depth and an interrupted search. Each engine must preserve an undefined
calculation or unsupported request as such. Agreement on a convenient
regular dataset is inadequate if the adapter silently turns these cases
into a definite causal answer.

Matched comparison must then separate four families of assumptions.
Constraint methods depend on their selected independence tests and graph
premises. Score methods depend on likelihood or surrogate criterion,
penalties and search restrictions. Functional methods rely on the declared
structural and disturbance restrictions, including the non-Gaussian
conditions developed earlier. Continuous optimization methods impose a
numerical acyclicity condition in addition to their statistical objective.
The selected other-language sources do not complete the census of
functional or continuous methods; the earlier Python comparison supplies
concrete alternatives without implying that a Julia or Rust equivalent is
absent. No implementation family should inherit another's causal
qualification solely because both return a matrix.

Only after these semantic checks should a bounded prototype compare runtime,
memory, failed requests and the consequences for an actual decision rule.
Freeze the source and environment identities, data units, baselines,
stopping criteria and failure account before final evaluation. These
requirements define a proposed comparison; the source inspections and exact
examples here do not claim to have executed it. The investment choice is
therefore specific: integrate a few well-understood paths, preserve useful
alternatives, and spend on porting only when an identified consumer or
measured bottleneck makes that additional responsibility worthwhile.
