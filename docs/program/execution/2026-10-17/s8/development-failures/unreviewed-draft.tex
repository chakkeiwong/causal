\chapter{Commercial alternatives, acquisition boundaries and the competitive capability gap}
\label{exec17:s8}

\section{The procurement question is a scientific question}
\label{exec17:s8-question}

A bank does not purchase ``causal inference'' in the abstract. It purchases a
workflow for a named decision, under a named information clock, with a named
population, data owner and loss function. A lending committee might ask whether
an eligibility threshold changes repayment, a treasury desk might ask whether a
rate change changes retained balances, and a servicing team might ask whether a
sequence of contacts is worth its cost. A commercial product can be excellent
for one of these questions and irrelevant to another. A common product proposal
therefore needs a comparison at the level of targets and assumptions before it
compares commands, languages or license units.

This chapter closes one part of that comparison. It uses the inspected GeNIe,
SMILE, BayesiaLab, Bayes Server, Stata, SAS, JMP, SPSS, Mplus, Amazon and
historical Azure material already audited in the working reader. GeNIe 5.0.R2
and SMILE 2.2.4.R1 identify their manual builds; several other official pages
are mutable or were retrieved after the 7 October 2026 cutoff. Those facts are
source limitations, not evidence that an uninspected edition lacks a feature.
No paid engine was run and no price below is a vendor quotation
\citep{exec13_genie_readme,exec13_smile_intro,exec13_bayesia_api,
exec13_ci_bayesserver_causality,exec13_ci_stata_causal_intro}.

The chapter has four contributions. First, it maps the 17 software areas to
documented commercial alternatives and to the present local capability. Second,
it identifies the semantic information that would be lost at an adapter
boundary. Third, it turns the documented license and deployment distinctions
into an executable acquisition design. Fourth, it gives exact hypothetical
cost, regret and information-value references. The monetary values are an
authored planning model. They are useful for deciding what a prototype should
measure; they are not evidence of a price, performance, or return on investment.

The rows are not claims that every named vendor implements every operation in
the row. They are a checklist for a matched comparison. For example, GeNIe's
pattern editor preserves an equivalence class and its documented Create DAG
command randomly orients unresolved arcs. BayesiaLab EQ searches equivalence
classes and gives fixed, forbidden and temporal restrictions different
semantics. A proposed adapter that maps both products to a single
\texttt{required\_edges} field has already changed the scientific input
\citep{exec13_genie_pattern,exec13_genie_bs,exec13_bayesia_eq}.

The local implementation column is deliberately narrower. The capability
manifest implements graph syntax review, a supplied-DAG back-door operation,
a supplied-moment residual inversion, deterministic sensitivity and a strict
observation clock. It does not implement general discovery, policy evaluation,
survival, report construction or job lifecycle. A completed ``unsupported''
response is an implementation boundary, not a negative result about a vendor
or about the scientific possibility of the method
\citep{exec16_commercial_runtime,exec16_commercial_matrix}.

\section{Graph discovery and model construction}
\label{exec17:s8-discovery}

\subsection{Equivalence is a deliverable}

GeNIe's PC documentation returns a pattern and describes a significance
threshold, maximum adjacency and a time-limit setting. Its Bayesian Search
route is a score-guided hill-climbing procedure with restarts and a structural
prior. The pattern editor identifies directed, unresolved and possible
hidden-common-cause arcs. Create DAG chooses directions randomly when a fully
directed network is required. These are useful capabilities, but the final
random representative is not new observational evidence. The proposed product
must store both the pattern and any selected representative, with the selection
seed and reason visible to the consumer.

SMILE makes the boundary concrete in code. Its PC call returns a
\texttt{DSL\_pattern}, can be interrupted by a progress callback, and reports
an interruption code. A time limit is checked after an iteration, so it is not
the same as a hard external wall-time guarantee. Pattern coordinates follow
the data-set variable order. A wrapper must reject a transposed or permuted
matrix rather than returning a plausible graph with the wrong node names
\citep{exec13_smile_pc,exec13_smile_pattern}.

BayesiaLab's EQ description supplies a different comparison. It searches
equivalence classes, treats fixed arcs as normal arcs, and takes forbidden arcs
and temporal indices into account. Thus two fields with similar names can have
opposite effects on the search. The integration contract should carry the
restriction kind, time index and class representation separately. A license or
REST call that returns a network is not evidence that the restriction was
interpreted as intended.

The banking consequence is immediate. Suppose a deposit-rate graph has an
unresolved rate--balance orientation. One representative says that the rate
changes balances; another says that a balance shock changes the quoted rate.
Both can fit the same observational law. The proposed service should return an
equivalence class or a refusal to answer an intervention query. A commercial
editor may be the best analyst-facing component, while the shared library owns
the typed class, provenance and refusal semantics. Building another graphical
editor would need a separate business case; porting SMILE is not an
open-source option because its manual describes proprietary development and
deployment licenses
\citep{exec13_smile_intro,exec13_smile_license}.

\subsection{The latent and supplied-model distinction}

Bayes Server documents causal optimization, an evidence-to-abduction-to-
intervention counterfactual workflow, and criteria such as back-door, front-door
and instrumental-variable routes. Its guide says that some helper functions
are available from version 10 and that the worked calculation can be performed
from 9.4. This is strong evidence of a documented abduction workflow. It is
not a complete domain theorem for every graph, nor an execution of the local
service. The request must state whether the output is a population intervention
or an individual structural counterfactual, and which exogenous-variable model
couples the factual and alternative worlds
\citep{exec13_ci_bayesserver_causality}.

BayesiaLab supplies graphical surgery, likelihood matching and contribution
analysis in the inspected pages. Stata supplies treatment effects and a
developed one-mediator workflow. These are valuable alternatives for specific
targets. Their assumptions remain part of the output: Stata's manual names
i.i.d. sampling, conditional independence and overlap; its mediation manual
addresses treatment--mediator and mediator--outcome confounding restrictions.
An adapter that returns a coefficient while dropping those conditions is a
semantic failure even if the numerical call succeeds
\citep{exec13_ci_bayesia_surgery,exec13_ci_bayesia_matching,
exec13_ci_stata_causal_intro,exec13_ci_stata_mediate}.

The buying route is therefore conditional. Reuse a commercial engine for a
supplied model when its edition exposes the required intervention or abduction
operation and its data movement and deployment rights are acceptable. Integrate
an open method when its source, license, numerical representation and target
semantics are compatible. Build the missing graph-class and assumption ledger
in the common library. Reject a direct port when the license, endpoint meaning
or hidden-state contract cannot be preserved. These are distinct decisions;
``use the package'' is not one of them.

\section{Effects, IV/RD and the limits of a command menu}
\label{exec17:s8-effects}

Stata's treatment-effect reference documents ATE, ATET and potential-outcome
means using regression adjustment, inverse-probability weighting, augmented
weighting and matching. Its caveats explain why i.i.d. sampling, conditional
independence and overlap matter. The \texttt{cate} postestimation path
evaluates a prespecified treatment-assignment policy. JMP's causal-treatment
documentation similarly defines positivity, consistency and conditional
exchangeability, while its uplift and treatment personalities address distinct
estimands. These capabilities set a high baseline for estimation. A new common
service must justify its cost by preserving target identity, evidence, clocks,
uncertainty and cross-tool failure semantics, not by adding another estimator
name \citep{exec13_ch_stata,exec13_ch_jmp_causal,exec13_ch_jmp_uplift}.

The IV/RD row is especially important for procurement. Stata's weak-instrument
postestimation describes confidence sets that can be finite, disconnected,
unbounded, whole-line or empty; its grid and simulation controls are exposed.
SAS/ETS SYSLIN supplies 2SLS, LIML, K-class, SUR and 3SLS system alternatives.
SPSS and JMP provide narrower equation or model-implied instrument paths. A
bridge that serializes only a point estimate loses exactly the result that is
most decision-relevant when the instrument is weak. The bridge should preserve
the set components, search bounds, grid, seed, covariance choice and whether an
empty set means model rejection or numerical noncoverage
\citep{exec13_ivrd_stata,exec13_ivrd_sas}.

For a credit threshold, the business request may be a local complier effect,
an all-applicant effect, or a reduced-form jump. The same columns and cutoff do
not identify all three. The proposed acquisition comparison should execute a
small public/generated fixture in which exclusion holds, then a negative control
where eligibility has a direct outcome effect. A commercial command can be the
reference implementation for the first fixture; it cannot make the second
restriction true. The cost of a licensed command is justified only if the
workflow preserves that distinction and reports the negative control.

\section{Time, panels and survival}
\label{exec17:s8-temporal}

GeNIe documents dynamic Bayesian networks and parameter learning for an existing
dynamic structure. Its parameter-learning page says that the structure is not
learned by that procedure and explains the node-and-time-slice column mapping.
SMILE's dynamic tutorial distinguishes initial from transition tables, lag order,
slice count and temporal evidence indices. SAS/ETS and Stata provide VAR,
SVAR, VARMAX and Granger-style operations, while SPSS TCM uses ``causal'' in
the Granger-predictive sense. Mplus provides intensive longitudinal and latent
dynamic models. These are substantial tools, but a predictive lag, a supplied
transition model and an intervention effect are different targets
\citep{exec13_ct_genie_dbn,exec13_ct_genie_learning,exec13_ct_smile_tutorial,
exec13_ct_stata_granger,exec13_ct_sas_causal,exec13_ct_ibm_tcm}.

The adapter must preserve sampling interval, time origin, state ordering,
calendar shocks, contemporaneous restrictions and the intervention regime. A
state array with swapped categories can pass type checks and reverse a
servicing action. A VAR test on shared monthly observations can be a useful
diagnostic while failing to identify a rate intervention. The proposal should
buy or reuse supplied-model temporal inference when it meets those fields and
build a common refusal when the question asks for an unsupported change of
regime.

Survival tools provide another concrete baseline. Stata's inspected
\texttt{stteffects} documentation excludes delayed entry, time-varying
covariates and multiple-record data in that command. SAS PHREG documents
counting-process records and competing-event output, but some options are
ignored under its EVENTCODE route. SPSS, Statistica, Minitab, JMP, NCSS and
Mplus each provide useful narrower conversion or reporting functions. The
local reference dispatcher returned completed unsupported responses for the
three authored fixed-treatment, competing-incidence and sequential-policy
identifiers. This establishes a present implementation gap and a route to a
matched public/generated bridge; it does not rank vendors or prove their
absence of other methods \citep{exec14_survival_stata,exec14_survival_sas,
exec14_survival_jmp,exec16_commercial_matrix,exec16_commercial_runtime}.

\section{Policy value, uplift and decision analysis}
\label{exec17:s8-policy}

Stata's \texttt{estat policyeval} evaluates a prespecified treatment-assignment
probability. GeNIe and SMILE influence diagrams compute expected utility for a
supplied model with decision nodes, information and costs. JMP uplift emphasizes
treatment differences in partitioning. Amazon Personalize documents train/test
recommendation metrics, including average rewards at rank. These capabilities
should be compared on aligned targets, not on the shared word ``policy''.

For a binary action, a prespecified static policy has value
\begin{equation}
 V(\pi)=\E\{\pi(X)Y(1)+[1-\pi(X)]Y(0)\}.
 \label{exec17:s8-static-value}
\end{equation}
For a sequential policy with history $H_t$, logging probability $b_t$ and
target policy $\pi_t$, the trajectory weight is
\begin{equation}
 W_T=\prod_{t=0}^{T-1}\frac{\pi_t(A_t\mid H_t)}{b_t(A_t\mid H_t)}.
 \label{exec17:s8-sequential-value}
\end{equation}
The second object requires action histories, positivity and an outcome clock.
It cannot be obtained by placing the last action in a static treatment column.
An influence diagram answers a supplied-mechanism utility question; a
recommendation metric evaluates a predictive ranking. The service must retain
which object was requested.

Azure Personalizer is a historical comparator. Its archived documentation
describes Rank and Reward calls, contextual and action features, delayed reward,
and a service that does not maintain individual user histories. It also records
that new resources stopped in 2023 and the service retired on 25 August 2026.
The migration recommendation to an open project does not establish estimator
or feature parity. AWS metrics and a retired hosted policy service cannot be
treated as evidence of a causal-policy guarantee
\citep{exec16_cp_azure,exec16_cp_aws}.

The proposed route is to keep a static policy adapter, a sequential off-policy
research module and a supplied influence-diagram adapter separate. First use a
public or generated trajectory fixture to test clocks, logging probabilities,
costs, action support, failure denominators and independent evaluation. Only
then consider a licensed engine trial. A model that refuses a sequential target
is preferable to a static score silently substituted for it.

\section{Language, deployment and semantic loss}
\label{exec17:s8-boundary}

SMILE's C++ engine and its documented wrappers for Java, Python, R, .NET and
COM are access paths to one proprietary engine. The licensing page separates
academic and commercial development, server deployment and end-user
redistribution. Bayesia's API page separates Java modeling and inference from
REST inference, describes customer-hosted model files for one configuration and
hosted models for another, and prices production by simultaneously loaded model
instances. The phrase ``Java API'' or ``Bayesia API'' therefore does not name a
single acquisition unit \citep{exec13_smile_intro,exec13_smile_license,
exec13_bayesia_api}.

The request contract should include:
\begin{enumerate}
\item a target and population with unit, horizon, currency and sign convention;
\item a graph or supplied model with endpoint marks, restriction types and
      unresolved-class representation;
\item treatment or action identity, assignment/logging law and observation clock;
\item estimator, uncertainty object, numerical controls, seed and refusal state;
\item artifact hashes, dependency versions, license entitlement, data location,
      interruption status and recovery identity.
\end{enumerate}

The consumer should see whether the result is documented, locally observed,
project-derived or proposed. A wrapper should preserve an interrupted SMILE
learning call as incomplete, preserve Bayes Server's intervention rather than
ordinary evidence, and preserve Stata's disconnected confidence set. It should
not coerce a vendor error or an unsupported target into a null estimate.

The recommended integration pattern is a narrow adapter plus a native semantic
ledger. For a proprietary engine, the ledger records the license, model
location, wrapper version, serialization and permitted deployment. For an
open-source package, it records the commit, license, dependency graph, source
anchors and whether the package can be adopted, wrapped, ported or rejected.
The common CLI and MCP surfaces expose the ledger and request envelope; they do
not make proprietary code open or transform a predictive metric into a causal
estimand.

\section{Scheduling a licensed engine}
\label{exec17:s8-scheduling}

Bayesia's production description makes simultaneous loaded model instances a
license quantity. A simple planning model is useful before a quote arrives.
Let job $i$ have supplied load-and-inference duration $d_i$, and let $m$ be the
number of permitted instances. For independent jobs and a nonpreemptive
schedule, the makespan is
\begin{equation}
 T_m=\min_{\text{assignment to }m\text{ instances}}
       \max_{j\leq m}\sum_{i\in j}d_i.
 \label{exec17:s8-makespan}
\end{equation}
This is a workload assumption, not a measured vendor rate. Three planning jobs
with durations 7, 5 and 4 take 16 units on one instance and 9 units on two
instances by placing the 7 and 4 jobs together. The calculation tells the
prototype to measure model-load time, queueing and failure recovery. It does
not establish that a production license permits that schedule or that the
engine scales linearly.

The same ledger must include model transfer, data residency, license-server
availability, retries, operator review and retirement. A cheaper per-instance
license can be dominated by a long load time or by the cost of converting a
pattern, state ordering or uncertainty object. Those terms belong in the
workflow cost, not in an unqualified engine benchmark.

\section{Exact hypothetical cost and route choice}
\label{exec17:s8-cost}

To make the acquisition decision reviewable, consider three routes for $n$
accepted requests in one planning year. The values below are deliberately
round and hypothetical:
\begin{align}
 C_B(n)&=420000+1.8n, &\text{build the common service},\\
 C_L(n)&=190000+5.6n, &\text{licensed adapter and conversion},\\
 C_H(n)&=285000+3n, &\text{hybrid: common ledger plus licensed engine}.
 \label{exec17:s8-costs}
\end{align}
The fixed terms include engineering, review and deployment preparation. The
variable terms include request preparation and operation. They do not include
an invented vendor quote. The exact pairwise crossings are
\begin{equation}
 n_{LB}=\frac{230000}{3.8}=\frac{1150000}{19},\qquad
 n_{LH}=\frac{95000}{2.6}=\frac{475000}{13},\qquad
 n_{HB}=\frac{135000}{1.2}=112500.
 \label{exec17:s8-crossings}
\end{equation}
Thus the licensed route is cheapest at low volume under this model, the
hybrid route is cheapest in the middle, and building the common service is
cheapest at sufficiently high volume. The ordering is a consequence of the
assumed costs, not a recommendation to purchase any named product.

At volumes 10,000, 50,000 and 150,000, the exact costs in USD are respectively
$(246000,315000,438000)$ for licensed, hybrid and build at the first volume;
$(470000,435000,510000)$ at the second; and $(1030000,735000,690000)$ at the
third. The maximum-regret route over these three scenarios is the hybrid route:
its regret is $69,000, compared with $340,000 for licensed and $192,000 for
build. This is a minimax decision over a declared volume set, not an expected
bank cost. The exact enumeration is reproduced in the accompanying S8
calculation record \citep{exec17_s8_examples}.

Semantic admissibility comes first. If a licensed route cannot preserve a
disconnected IV set, a graph class, or a sequential policy's logging law, its
cost is not comparable to a build route that can. The route is then rejected
for that target regardless of its nominal price. The prototype should measure
the fraction of requests that require conversion, refusal or human review and
replace the planning terms with observed quantities.

\section{The value of a compatibility signal}
\label{exec17:s8-signal}

A paid trial should be requested only when a less expensive signal can change a
decision. Consider 50,000 requests. The build cost in the model above is
$510,000 and the licensed success cost is $470,000. If the licensed conversion
fails, add a stipulated $250,000 remediation cost. Before a compatibility test,
let the probability of success be $3/5$. The expected licensed cost is then
$570,000$, so the safe build route is selected.

Suppose a public/generated semantic fixture has sensitivity $19/20$ and a
false-positive probability $1/20$, with test cost $15,000. Bayes' rule gives
\begin{equation}
 \Prob(+)=\frac{59}{100},\quad
 \Prob(\mathrm{success}\mid +)=\frac{57}{59},\quad
 \Prob(\mathrm{success}\mid -)=\frac{3}{41}.
 \label{exec17:s8-signal-posterior}
\end{equation}
The expected licensed cost after a positive result is $478,474.576\ldots$,
below build; after a negative result it is above build, so the policy chooses
licensed after $+$ and build after $-$. Including the test costs
$506,400$, a saving of $3,600 against the no-signal
choice. The positive value is conditional on the stipulated signal law. It does
not justify a vendor purchase; it identifies the evidence a cheap prototype
would need to collect before a paid trial.

The signal may instead be a graph-conversion fixture, a survival row-reconciliation
fixture or a policy-clock fixture. Its acceptance criterion must include every
failure and unsupported target. A test that measures only successful calls can
make the signal look more informative than it is. The exact posterior and route
choices are project calculations, not observed vendor behavior
\citep{exec17_s8_examples}.

\section{Adoption decisions and remaining competitive gaps}
\label{exec17:s8-decision}

The comparison yields six concrete decisions.

\begin{enumerate}
\item \textbf{Reuse a commercial editor} for analyst graph construction when
      the bank accepts the edition, licensing and model-export boundary. Keep
      the unresolved class and source evidence in the common ledger.
\item \textbf{Integrate a licensed engine} only for a named supplied-model,
      intervention or inference profile whose wrapper, error and deployment
      behavior pass a matched public/generated fixture.
\item \textbf{Adopt open-source components} when the original source, license,
      dependency rights, coordinate convention and uncertainty object can be
      preserved. A package's presence in a catalog is not a runtime result.
\item \textbf{Port selectively} only for a narrow algorithm whose semantics,
      numerical tolerances and adverse cases can be reproduced. Proprietary
      SMILE or hosted vendor implementations are not porting candidates.
\item \textbf{Build the semantic ledger and refusal layer} because it spans
      graph classes, target clocks, uncertainty, artifacts and licenses rather
      than one estimator. This is the proposed product's defensible common
      capability, still unqualified at bank scale.
\item \textbf{Reject a route for a target} when it changes the estimand,
      drops unresolved structure, cannot preserve an uncertainty set or lacks
      a lawful deployment path. Rejection is a successful proposal outcome.
\end{enumerate}

The gaps remain substantial. The local service has no general discovery or
sequential-policy runtime; no commercial engine has been executed here; exact
edition parity, paid prices, embedding rights and support terms remain unknown
for many families; and arbitrary latent graphs, dependent learners, authentic
assignment truth and bank economics remain open. A complete census across all
17 areas requires additional primary manuals and owner inputs. The present
chapter narrows what should be measured and purchased; it does not claim that
the competitive survey is closed.

\section{A prototype-to-purchase protocol}
\label{exec17:s8-protocol}

The next public/generated comparison should freeze one target from each of four
journeys: a graph-class intervention query, a weak-IV set, a competing-event
row conversion and a fixed-history policy value. For each target, freeze the
input schema, unit, clock, graph/model, method, uncertainty object, license
mode, seed, resource budget and stopping rule. Run the common ledger, a selected
open-source reference and a documented commercial route when accessible. Report
semantic equivalence, refusal/unsupported counts, numerical error, uncertainty
shape, preparation and review time, memory, queueing, recovery and full cost.

The study must include negative controls: a randomly oriented graph, a
transposed node matrix, an unsupported delayed-entry survival record, a
nonpositive logging probability, a direct-effect IV violation and a recommendation
metric presented as though it were a causal value. A system passes only when it
preserves the refusal or identifies the changed target. The full denominator
includes unavailable originals, failed conversions and manual reviews.

An accepted public/generated result would justify a narrow paid trial. It would
not justify a bank deployment. The paid trial would bind the exact edition,
entitlement, data residency, service account, operating platform and publication
rights, then repeat the frozen matched protocol. Authentic bank assignment,
audit truth, accepted loss and institutional economics remain later inputs.

\section{Conclusion}
\label{exec17:s8-end}

Commercial alternatives already provide meaningful graph, model, estimator,
survival, policy and deployment capabilities. The proposal's gap is not a lack
of commands; it is the lack of a common contract that keeps target meaning,
ambiguity, uncertainty, numerical state, data clock, rights and refusal visible
across those commands. A hybrid acquisition route is a useful planning default
under the displayed hypothetical costs, while a cheap compatibility signal can
change a route only under a declared signal law. The immediate work is therefore
the public/generated matched protocol and the semantic ledger. Prices, runtime
parity, bank truth, independent acceptance and ROI remain open evidence, as the
proposal must say plainly.
