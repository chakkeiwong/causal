\chapter{Application and component contracts}
\label{sec:engineering-specification}

\begin{questionbox}{Can a department operate the proposed product?}
What should an analyst, application operator or builder receive from a
supported calculation? When the application also requests action, how does
it preserve the native account, authority, delivery and corrected readout?
\end{questionbox}

A useful application has to survive an untidy working day: a record arrives
late, a customer withdraws permission, or a delivery acknowledgement goes
missing. Its public operations must tell the user what happened and preserve
the account. The complete product connects common data, statistical estimation,
financial accounts and constrained decisions to distinct banking workflows.
The retained suite demonstrator supplies a complete retail card activation
and retention cycle and bounded synthetic packs for commercial banking,
wealth and asset management, and investment banking and markets. That
specified demonstrator is one implementation boundary within the broader
product. Common data and execution interfaces serve each domain while preserving its
financial definitions and decision rules. Customer data and commercial
authority remain within each approved boundary; a shared software component
does not grant access to another department's records or imply a joint launch.

The retained demonstrator and its stable requirements are documented in \cref{sec:history-engineering}. Its obligations remain applicable to that scope; the component and native application contracts below address the wider offering.

Before implementation, the architecture review maps each selected domain's
valuation, permission, suitability and timing constraints to a shared service,
local adapter, simulator or explicit exclusion. An incompatible contract
assumption must produce a recorded rejection or a versioned resolution with
regression obligations. No mandatory conflict may remain hidden behind a
special exception. The suite integration cases in
\cref{sec:acceptance-suite} subsequently test those decisions in the running
application.

\section{Three consumers of the same scientific calculation}
\label{sec:engineering-consumers}

A direct analyst needs a callable operation with explicit inputs, outputs,
assumptions and diagnostics. A fitted demand component can return a useful
model and prediction without creating a campaign. Its contract includes the
population, menu, outcome, information date, preprocessing and uncertainty.
The analyst supplies suitable data and interprets the result at that scope.
The operation must describe unsupported requests clearly enough for the
analyst to choose another method or obtain another observation.

A supplied-app user needs those quantities organized around a banking task.
The application adds native terminology, configuration, a useful comparison
and an intelligible report. If it requests action, it also needs current
authority, capacity, delivery and recovery. Its contract describes what a user
can complete with the installed version and what happens when information is
missing. A local outbox, an acknowledged external delivery and a mature
financial result are different outputs.

\Needspace{9\baselineskip}
A custom-app builder needs stable public composition points. Its application
can present a different interface or combine supported components for a new
brief, while preserving the target and ownership information those components
require. The builder does not need to copy the library's algorithms. It does
need to test the changed mappings and economic assumptions, document its
configuration and name the maintenance owner. A coding agent assisting that
work has the same responsibility to use actual supported interfaces.

\subsection{Configuration, extension and authority}

Configuration selects supported terms, model settings and reporting choices
within the declared input domain. An extension supplies a new native mapping,
account or method under a reviewed public contract. A scientific change alters
the population, comparison, observation model or economic target. These
categories can overlap: a new permitted offer may be syntactically valid but
outside the evidence used to fit its response. The resulting application
needs an explicit unsupported-case result or additional evidence.

Trusted host configuration supplies runtime grants, current controls and
prospective validation criteria. A request can ask to evaluate or operate; it
cannot manufacture those permissions by supplying an approval field. The
local research implementation assumes a trusted filesystem owner. It does
not isolate a process that can rewrite its host configuration. A deployed
bank boundary must match its actual identity and access arrangements.

\section{A construction trace through public components}
\label{sec:engineering-construction}

Begin with the native deposit example and a brief to compare approved funding
offers. The builder runs the documented Python or terminal journey against a
fresh synthetic project, retaining its actual requests and responses. Demand
and persistence fitting consume the declared histories; holdout validation
precedes registry activation. Policy construction combines candidate and
incumbent finance, permission and capacity. Preview exposes that proposed
comparison before local dispatch. Measurement then consumes distinct mature
observations and retains every planned customer, including failed delivery.

The builder first changes a supported contact capacity. The change must enter
the host's actual resource configuration and lead to a newly reconstructed
allocation. Reusing an old action list after changing the capacity would break
the application even if its model predictions remained valid. The changed
request and resulting allocation are retained, and the earlier decision stays
readable. The example's invoice correction then checks that a later readout
can change without rewriting what was known at the earlier cutoff.

Now consider a request to reuse this application for mortgage refinancing.
Temporal preparation, registration and cash-date functions remain relevant.
The native target changes. The builder selects the home-finance interface,
supplies an existing loan and its ownership path, and compares refinancing
with retaining that claim. The household's contractual saving is a separate
output. The new application cannot obtain the bank's incremental value by
multiplying the deposit response probability by a replacement loan's gross
interest. That composition mixes a different response event, omits the old
claim and fails to identify the requested intervention.

This invalid construction is useful to test because its inputs can all be
numerical and well formed. Component checks should reject incompatible
explicit targets; substantive review must also examine the truth of the
supplied declarations. A builder who falsely labels a response as causal has
not supplied causal evidence. An accepted schema cannot establish that a
bank-owned source really measures the field its label describes.

\subsection{Results that remain useful when a request is incomplete}

A result can be a supported estimate, a conditional scenario, a sensitivity
range, a set of compatible values or a specific missing-input explanation.
The application displays the result in those terms. It must not silently
convert a range into a point or combine marginal intervals into an invented
joint distribution. The evidence rules in \cref{sec:evidence-decisions}
determine which comparisons can follow from each form.

The custom interface should expose the source result and the assumptions
needed to interpret it. A saved explanation refers to the actual calculation,
with versions and dates. It can explain why an approved action was suppressed,
why an incumbent was retained or why a total is unavailable. Narrative
fluency is not a substitute for that correspondence. A user should be able
to follow a displayed claim back to the relevant result without inspecting
undocumented internal state.

\subsection{Testing the boundary after a change}

Construction tests include a valid public journey, an economically incompatible
request, missing history and a supported upgrade. Reconstruction of a small
account uses separate arithmetic or observed source totals. Replaying the
same production formula would miss a shared sign error. A maintained example
also records which behaviors depend on synthetic assumptions, broad teaching
margins or replay authority. The independent construction evaluation uses a
separate brief, while intended-user evaluation examines whether the resulting
application helps the actual job.

\section{A report the banking user can interpret}
\label{sec:business-report-contract}

A report begins with its banking question, original population, incumbent,
information cutoff, outcome horizon and economic owner. It identifies the
returned quantity as observed accounting, prediction, a conditional scenario,
an estimated effect or a range. The reader sees the comparison, its decomposition
and relevant uncertainty before the release/version information needed to
reproduce it. The native chapters give the account fields for each application;
\cref{tab:builder-auto-report} is a complete executed analytical example.

These outcomes are presentation requirements tied to the actual operation.
Direct auto prediction produces a conditional comparison; its unsupported
requests return specific native errors. Native operating applications expose
preview, dispatch, measure, readout and correction only at their documented
interfaces. A report specification for another application is implemented and
verified through its owning native release. The common field names do not
establish that all adapters currently implement every outcome.

The source of a failure determines its remedy. A wrong currency is repaired
at the mapping or configuration; missing outside purchases require additional
observations or a narrower question; an unfavorable economic result can be
scientifically correct. The user should receive that explanation in the
language of the banking task, with the technical trace available for the
maintainer. A generic error code alone is insufficient for an operator to
choose the next valid action.
